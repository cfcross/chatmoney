# ToC Data Intake

> 何时加载：接新数据源、写字段映射、产出意图矩阵 / 政策树 / 知识缺口，或要判断「这份数据能不能进引擎」时。
> 先读 `docs/ROADMAP.md`（阶段与验收门）与仓根 `AGENTS.md`（红线）。

## 1. 要产出的三样东西

| 产出 | 列 | 判据 |
|---|---|---|
| 意图覆盖矩阵 | 意图 / 典型原话（3–5 条真实样本）/ 触发词 / 期望处理 / 自动化等级 / 依据 | 抽样人工判对率 ≥ 80%，分歧点写回矩阵 |
| 政策树规则 | 条件 / 动作 / 金额上限 / 时间窗 / 品类例外 / 证据要求 / 升级条件 | 每条都有依据（平台规则、商家承诺或法务口径）；无依据不写 |
| 知识缺口清单 | 问题原话 / 出现频次 / 应回答什么 / 缺哪份资料 / 归谁补 | 来自引擎召回不到的真实提问，不是凭空列的 FAQ |

## 2. 与引擎表的对应（字段以 `app/schema.py` 为准）

| 逻辑对象 | 实际表名 | 关键字段 | 需要提供的内容 |
|---|---|---|---|
| 商品 | `products` | `name`、`version_ref` | 商品/服务目录，`version_ref` 对应一份资料版本 |
| 客户 | `customers` | `name`、`profile`(json) | 档案与结构化标签；`profile` 不放整段原文 |
| 账号 | `accounts` | `product_id`、`enabled`、`capabilities`(json) | 店铺/渠道账号与能力清单（能否主动私信、是否需审核） |
| 会话准入 | `conversations` | `permitted`、`opted_out`、`window_until` | 退订与私信窗口必须真实，不得默认放行 |
| 订单 | **`mock_orders`** | `customer_id`、`product_id`、`shipping` | 订单与物流；当前为模拟数据，接真实源后替换 |
| 线索 | **`source_records`** | `customer_id`、`product_id` | 线索来源记录 |
| 资料 | `kbs` / `docs` / `chunks` / `snapshots` | 文档、分块、快照 | FAQ、政策、参数表；改内容走新快照，不改历史 |

**表名与逻辑名不一致是已知坑**（`orders`→`mock_orders`、`leads`→`source_records`）：写映射前先读 `schema.py`，不要按接口文档或语义猜。

## 3. 每条数据必须带的四样

1. **来源**：URL / 接口 / 文件名 + 取得方式。
2. **时点**：采集时间（UTC），以及数据本身的生效时间（如价格有效期）。
3. **口径**：字段定义与单位（含税与否、件/箱、含运费与否）。
4. **可重跑**：脚本每次输出可 diff；同一天跑两次不产生重复行（幂等键＝来源＋主键＋版本）。

## 4. 采集前先确认（缺一项就停下来问）

- [ ] 平台条款允许这种读取方式；需要授权的先拿授权。
- [ ] 只读还是写？写操作（点赞、关注、私信、评论）一律单独授权、限额、留回执。
- [ ] 限速与并发：目标站点能承受多少；有反爬信号就退避，不硬闯。
- [ ] 样本量与时间窗：覆盖哪些品类、时间范围、多少条；先小样本验证解析正确再放量。
- [ ] 留存与脱敏：PII 遮罩规则、保留期、谁能看。
- [ ] 缺口怎么回流：召回不到的问题记在哪里、谁负责补。

## 5. 踩过的坑（症状 → 原因 → 正确做法）

| 症状 | 原因 | 正确做法 |
|---|---|---|
| 按 `orders` 写 SQL 找不到表 | 实际表名是 `mock_orders`，`leads` 也是 `source_records` | 以 `app/schema.py` 为准；写映射时标注实际表名 |
| 拿 O7/O8 之类订单做分析，结论对不上真实业务 | 这些是种子生成的模拟数据 | 先确认数据是模拟还是真实；模拟数据只能验证链路，不能出业务结论 |
| 搜索「查无此物」，但东西明明存在 | 查询被退化成单字匹配、反爬页返回 202、连续请求被限流返回空 | 校验命中内容里是否真出现关键词；空结果要区分「确实没有」与「被挡/被限流」 |
| 上一轮抓的 html 或脚本找不到了 | 留在了临时目录 | 中间产物落工作区路径 |
| 同一个事实两个字段各写一份，后来不一致 | 没有指定唯一归属 | 一个事实只有一个归属字段，其它地方引用 id |
| 文档里混进繁体字、内部称呼、作者自己的绝对路径 | 草稿直接抄进随仓文档 | 统一简体通用写法；不写内部称呼与绝对路径；不给外部读者指路到工作机上的目录 |
| 为跑通链路先写死返回值，后来忘了 | 没有标注 | 写死就标 `MOCK`/`TODO`，并进知识缺口清单或 issue |
| 把搜索摘要当事实写进政策树 | 摘要不是原文 | 政策依据必须能指到原文或快照 |

## 6. 验收清单（每次交付前逐项打勾）

- [ ] 采集脚本在干净目录能一次跑通；两次运行输出可比对（除时点字段）。
- [ ] 任取 10 条数据，能顺着来源追到原始页面或接口响应。
- [ ] 抽样 30 条意图标注，人工判对率 ≥ 80%；分歧点已写回矩阵。
- [ ] 政策树每条都有依据与上限；无依据的已删除或标为待确认。
- [ ] 缺口清单每条都对应具体缺的资料，不是「大概缺资料」。
- [ ] 文档里没有 PII、没有内部称呼、没有只有在作者机器上成立的路径或临时做法。

## 7. 维护本 skill

- **可直接改**：坑表格（新坑按三列格式补）、表映射（引擎改了结构就更新）、验收清单条目、采集前确认项。
- **先问**：删掉某条验收项、放宽 PII 或只读优先的要求、改三份产出的列定义。
- **禁止**：把模拟数据写成真实口径；为了赶进度删掉「来源与时点」；写入绝对路径、主机名、凭据、内部称呼。
- 改完自查五项：frontmatter 闭合、只含 `name`/`description`/`whenToUse`/`metadata`、`name` 与目录名一致、description 不过长、无历史外来词。
