## 0. 术语表

| 词 | 含义 |
|---|---|
| 引擎 / ChatMoney | 共享的会话处理服务（PR #1）。接收客户来信，产答复草稿、渠道回执或人工工单 |
| ToC 业务线 | 面向消费者：店铺客服、社群内容、直播 |
| ToB 业务线 | 面向企业：外联、报价、合同 |
| claim（话术账本） | 一条「可以对外说的话」，含出处、有效期、适用范围、审批人。对外的每句话都应能追到某条 claim 或某份知识快照 |
| 回执（receipt） | 渠道对「消息是否送达」的确认。`unknown` 表示结果不明，必须冻结、不重试 |
| 三段式 | 意愿（要不要说）→ 许可（能不能说）→ 回执（说成了没有），三态齐备才算已发送 |
| 灰度 | 小范围、可随时停止的正式流量。灰度前必须先通过离线评测 |
| 影子模式 | 只读不写：系统照常处理，但不向客户发出任何内容 |
| RLS | 数据库行级权限隔离，保证一个企业看不到另一个企业的数据 |
| 契约 | 引擎对外承诺的接口与数据格式。改动契约需先与引擎维护方确认 |

## 1. 范围与协作

平台本身是完整的：一套共享引擎 ＋ ToB、ToC 两条业务线。下表说明各部分的内容与当前阶段，不改变仓库边界。

| 范围 | 内容 | 当前阶段 |
|---|---|---|
| 共享引擎 | 会话处理、知识库、分层记忆、政策判定、渠道回执、人工接管、管理工作台 | 已交付 V1.1（PR #1）；内核演进由引擎维护者主责 |
| ToB 业务线 | 企业外联、报价、合同、线索管理 | 由对应维护者推进 |
| ToC 业务线 | 店铺客服、社群内容、直播 | **当前阶段重心**：数据收集与需求分析（数据管道、意图覆盖矩阵、政策树规则、知识缺口、话术评测） |
| 交叉部分 | `policies` 规则注册表、`memory` 主表、渠道回执、工单队列、工作台权限 | 任一方改动前先与另一方确认 |

## 2. 起点（2026-11-15）

- 引擎代码在 PR #1 的分支上：29 个端点、22 张表、6 个前端页面、91 个用例；本地实测 90 通过 / 1 失败，失败原因是接口规范文档 `docs/architecture/` 未入库。
- `main` 分支尚无已合并内容；引擎目录（`app/`、`migrations/`、`scripts/`、`tests/`）待 PR #1 合并后进入主干。
- 引擎已具备：数据行级隔离（RLS）、角色版本发布与历史版本固定、知识库快照、记忆人工纠正与变更审计、发送回执（含 `unknown` 冻结）、幂等、崩溃恢复。
- 引擎尚缺：真实渠道（目前只有模拟渠道）、政策规则内容（写死在代码里）、claim 层、知识缺口回流、对外拟真能力（消息分段、语气分布、真人感判别）。

## 3. 阶段与验收门

周与门槛数值均为初值，未经实测不得作为对外承诺。

| 阶段 | 目标 | 验收门（全部通过才进入下一阶段） | 不达标时 |
|---|---|---|---|
| **P0 数据与需求基线** | ToC 数据可重复采集；意图矩阵与政策树成型 | ① 采集脚本可重复运行且输出可逐次比对；② 每条数据可追到来源与采集时点；③ 意图覆盖抽样人工判对率 ≥ 80%；④ 政策树每条规则都有依据与上限 | 缩小品类范围，不凑全量 |
| **P1 引擎接入** | 在引擎上跑通一条完整 ToC 会话 | ① 同一输入、同一版本、同一结果（可回放）；② `unknown` 回执被冻结且可观测；③ 记忆纠正有留痕；④ 知识快照与商品资料一致 | 回放做不到则不进入评测 |
| **P2 离线评测** | 不投放即可判断话术可用性 | ① 合规违规 0 例；② 真人感判别通过率 ≥ 80%；③ 对话推进率 ≥ 60%；④ 平均轮次 4–9；⑤ 回归集可一键重跑 | 不达标则调整角色设定与流程，不进入灰度 |
| **P3 店铺客服灰度** | 达到人工客服基线 | ① 解决率不低于人工基线；② 差评率不上升；③ 平台考核 0 扣分；④ 例外 100% 进入人工队列；⑤ 灰度前完成 2 周影子模式 | 出现扣分即停止写入，退回影子模式 |
| **P4 社群内容** | 从选题信号到成品稳定产出 | ① 审核退回率 < 20%；② 违规下架 0；③ 夜间不主动发布；④ 消息拆分按语义点，不按标点机械切 | 退回率降不下来则降低产量、改为人工选题 |
| **P5 直播** | 以产品为主体的低变化直播 | ① 回复延迟 P95 < 2.5 秒；② 错价事故 0；③ 导播台三个按钮（静音／切预录／切真人）实测有效；④ 留言事件不丢不重 | 延迟压不住则改为全预录加定时脚本 |

## 4. 需要引擎侧确认的四个契约问题

以下四项都属于引擎的对外格式，需由引擎维护者确认后再定实施方案。

1. **政策规则数据化**：目前政策规则写在代码常量里（`policies.REGISTRY`），无法表达 ToC 需要的金额上限、时间窗、品类例外。建议改为数据表加版本，代码只保留评估逻辑。
2. **单条发送**：当前一次只发一条消息（`Sender.__call__(ex, text, sources)`）。若需要 1–3 条分段发送，需把单条文本改为消息列表，长度为 1 时行为不变。
3. **逐句出处**：当前只判断「有或没有可引用内容」（`grounded = bool(chunks or facts)`）。若要求每句话都有出处，需让生成结果携带 claim 引用，并逐句校验；缺出处的降级为草稿。
4. **渠道能力描述**：当前模拟渠道自己生成回执（`MockChannel.accept()`）。接入真实平台需要能力标识（能否主动发、是否需审核、字数上限）、发送／查询状态／拉取接口，以及分渠道限额。
