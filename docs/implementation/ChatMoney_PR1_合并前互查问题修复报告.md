## 六、Research Worker 同站竞争

领取 queued 任务时写入租约。成功获得站点锁后才进入 fetching。锁由专用数据库事务持有，覆盖抓取和证据入库。事务提交、回滚或进程断开都会释放锁，生成分析时该站点已可供下一个任务读取。

同一站点忙时，任务保留 queued 和原编号，清空领取令牌，使用现有到期字段延迟 4 至 8 秒。连续竞争合并为一项 site_wait 事件。在到期前轮询不会重新领取。此路径没有 HTTP、LLM 和业务重试消耗。已保存证据的任务可直接继续分析。中断时如果请求可能已经发出，原任务记录 INTERRUPTED，供人工核查，以免二次调用。

真实 PostgreSQL 并发用例检查了两个任务的读取和模型次数、到期前不可领取、最终分别完成一次，以及 Worker 进程终止后的恢复。普通业务队列沿用原有重试与退避。对练和研究合用 Worker 时按租户及队列轮转，双租户连续有任务的回归覆盖了两轮分配。生产持续高负载下的排队时延尚未压测。

## 七、知识上传租户隔离

租户 ID 在当前模型里是文本。迁移通过 PostgreSQL Identity 给每个租户分配唯一整数，并加唯一约束。锁键为两个 int4 参数，分别表示租户专有编号的负值和槽序号。该键空间与其他 Worker 的单个 bigint 锁互相独立。API 进程通过各自的数据库连接参与同一限额。完成和异常时释放，失效连接丢弃，进程退出由数据库释放。

默认每租户一个上传槽。客户端一次性提交 multipart 请求，服务端按 256 KiB 分片计数和校验 SHA256。默认总时限 3600 秒、空闲时限 120 秒。持续提交小块无法延长总时限。以 3 Mbit/s 规划时，10 亿字节约需 2667 秒，剩余约 933 秒应对开销。纯传输的理论下限约为 2.22 Mbit/s。在 2 Mbit/s 上纯传输就需 4000 秒，支持此带宽的部署可将总时限设为 5400 秒。代理原有客户端读取空闲时限为 120 秒，关闭请求缓冲，向上游写入的空闲时限为 300 秒。慢速场景通过受控时钟和暂停数据流验证。另实测终止持锁的上传进程，另一租户仍可用；数据库识别断开后原租户恢复可用，本次观测约 15 毫秒。

已在独立库验证带现存租户的 `0013_company_research → pr1_upload_lock_keys` 迁移、编号唯一和降级后保留租户行。桌面后续版本另有空迁移 `0017_merge_upload_lock_keys`，用于汇合其 `0016_outlook_drafts` 分支；它只适用于含后续版本的工作区。
